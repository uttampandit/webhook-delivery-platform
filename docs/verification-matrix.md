## Scheduler and replay review

Reviewed `internal/store/claims.go`, `finalize.go`, `recovery.go`, `replay.go`, `events.go`, and `internal/delivery/worker.go`/`http.go`. Claims and reaper lock deliveries using `FOR UPDATE SKIP LOCKED`, then mutate attempts; finalization locks delivery before matching running attempt. Replay locks one tenant-scoped delivery before audit insert and state update, rechecks keys after lock wait in READ COMMITTED, and resolves unique-key losers with a fresh statement. Existing-key retries resolve before current-state rejection. No lock-order or stale-token bug was found in this review.

Claim COMMIT or subsequent send-data load errors expose no send data. Finalization/recovery/replay uncertain commits return explicit errors; caller must not infer that the remote effect failed. Network HTTP is outside DB transactions. Finalizer checks DB clock after acquiring the lock and fences status/generation/token/lease. New replay-cycle regression confirms an old claim cannot overwrite the new attempt. Sender fencing protects database writes; it cannot retract an external request already sent.

Synthetic SQL fixtures may force lease/due-time conditions in repository tests. The real due-time finalization test, actual worker HTTP isolation test and real receiver socket-loss tests complement them. Process-death timing is still pending Task19. No broader project/release gate is claimed.
